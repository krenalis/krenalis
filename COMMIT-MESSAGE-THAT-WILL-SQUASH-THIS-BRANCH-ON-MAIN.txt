cmd, core: add the `-migrate-db` and `-finalize-db` flags (#2778)

Currently the database updater is written before a release and thrown
away after it (see #2767). Also, it cannot be used on AWS ECS, where a
one-off task must migrate the database before the service is updated,
and where the instances of the previous and of the new release run
together during a rolling deployment.

This commit lays the groundwork for the updater, so that we can start
using it, also on AWS. It aims to be correct, not to be the ideal
updater: both the mechanism and the policy for writing the upgrade code
of each release can be refined over time, as we gain experience with
real upgrades.

The idea of this commit is to upgrade the database in two separate
steps: the migration and the finalization. The migration runs before the
instances are replaced, and must not break those of the previous
release. The finalization runs once only new instances are left. When it
is done, the database is "finalized", and the previous release can no
longer run on it.

In detail, the migration is started with the new "-migrate-db" flag. It
initializes the database if it is empty. Otherwise it migrates a
finalized database of the previous schema version with "migrate", and
records the new schema version as not finalized. It does nothing on a
database already at its schema version, or at the next one but not
finalized, as after a rollback to the previous release, and fails in any
other case, such as a skipped release.

The finalization, instead, is started with the new "-finalize-db" flag.
It runs "finalize", and records the schema version as finalized. It does
nothing on a database already finalized, or at the next schema version
but not finalized, as after a rollback to the previous release. It must
run only when no instance of the previous release is running anymore,
which it does not check; otherwise the behavior is undefined and may be
destructive.

Both flags are permanent (that is, they are designed to remain within the
Krenalis command even between releases, unlike what we used to do before), exit
when done, and can be combined (to carry out both the migration and the
subsequent finalization). Each runs in a single transaction, under the advisory
lock used by the database initialization, and with a 5-second lock timeout
(so that a statement that cannot acquire a lock within that time fails, instead
of waiting and making the running Krenalis instances queue behind it). Both
operations can be retried until they succeed, and run concurrently from several
instances. To know where the database stands, the
database records its schema version, an integer incremented only by the releases
that change the database, and whether it has been finalized. By convention, a
database of v0.48.0 (which is the version already released, and which therefore
lacks such a mechanism) is taken to be at schema version 1, finalized.

At startup, Krenalis now checks the schema version of the database. It
starts if the database is:

- at its schema version, finalized or not;
- at the next schema version, not yet finalized; this occurs, for example, in
  the case of a rollback of Krenalis to a previous version. As the database has
  not yet been finalized, compatibility with the previous version of Krenalis is
  guaranteed.

It refuses to start if the database is:

- at an older schema version, not yet migrated;
- at the next schema version, already finalized;
- at any later schema version.

The two releases also exchange notifications and NATS messages while
they run together. Keeping them compatible is not covered by this
commit, and is still open (see #2796).

"migrate" and "finalize" are written when a release that changes the
database is prepared, from the notes in
"core/internal/initdb/RELEASE-UPGRADE.md", which now separate the
migration from the finalization, and are emptied after the release.

The upgrade lives in the "core/internal/initdb" package, whose name now
covers only part of what it does. The package keeps its name for now;
whether to rename it will be evaluated in the future.

Add test helpers for the upgrade test of each release, and update
"AGENTS.md" and the "release-upgrade" skill.
